## Codebase Patterns
- Pre-existing TypeScript errors exist in: auth routes, API key routes, player pages, and airtable services
- All Airtable operations go through src/lib/services/airtable.ts - never call Airtable directly
- Use airtable-client.ts table constants (USERS, REPORTS, COMMENTS, API_KEYS) for table references
- Components use dark theme classes: text-text-primary, text-text-secondary, bg-bg-elevated, etc.
- API responses follow format: { success: boolean, data?: T, error?: string, message?: string }
- Auth checks use getServerSession() with authOptions from src/lib/auth.ts
- Forms use React Hook Form + Zod validation pattern
- Client-side data fetching uses SWR or fetch in useEffect
- Cloudinary service at src/lib/services/cloudinary.ts handles media uploads
- UserProfile type already has bio, avatar, location, website, discord, steam fields
- Player page at /player/[username] now fetches real data from API
- Notifications table (NOTIFICATIONS) must be provisioned in Airtable with fields: user_id, type, title, message, related_report_id, is_read, created_at
- Airtable .create() with plain objects needs `as any` cast or `(base(TABLE).create as any)({...})` to avoid TS2769 errors
- Discord webhook fires only on status=Verified, configured via DISCORD_WEBHOOK_URL env var
- Use stopPropagation on inner links within card components that are already wrapped in Link
